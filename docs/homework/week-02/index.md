## 项目选题

### 最终选题

- ***\*项目名称\****：CampusTrade 校园二手交易平台

### 选题说明

***\*要解决的实际问题和业务背景\****

每年毕业季和开学季，高校学生都会产生大量闲置物品（教材、数码产品、生活用品等），这些物品仍有较高使用价值，但缺乏高效的校内流转渠道，大多被低价处理或丢弃，造成浪费；同时新生和在校生又有低价购置这些物品的刚性需求。通用二手平台面向全社会，信任成本高、以邮寄为主，弱化了校园内当面交易的天然优势。一个限定校园范围、以面交为主的二手交易平台能显著降低信任与交易成本。

***\*主要目标用户及其需求\****

- 游客：浏览商品、了解平台，注册成为用户；
- 学生（买家）：搜索商品、下单购买、与卖家沟通、跟踪订单、评价；
- 学生（卖家）：发布/管理闲置商品、处理订单、与买家沟通；
- 管理员：认证审核、违规商品与内容管理、举报处理、数据概览。

***\*选择该题目的原因\****

- 业务场景贴近校园生活，需求真实、边界清晰，需求分析不需要过多外部调研；
- 业务天然划分为用户、商品、订单、消息等聚合，与微服务拆分边界高度吻合，非常适合作为课程演进的载体；
- 交易闭环完整（发布 → 搜索 → 沟通 → 下单 → 交付 → 评价），既能做核心流程，又能自然引出消息队列、分布式事务等进阶主题；
- 不依赖真实支付和物流，规避了合规风险，可以把精力集中在课程重点——微服务的设计、拆分与部署上。

***\*项目的初步边界\****

- 范围：Web 端学生功能（注册登录、商品发布与管理、搜索、下单、消息、评价）+ 简单管理后台；校园邮箱认证；线下交付、平台不处理真实资金。
- 不实现：真实在线支付、移动端 App/小程序、物流快递、个性化推荐、多校加盟运营。

***\*为什么适合逐步演进\****

功能模块之间耦合度低，可以按「用户 → 商品 → 订单 → 消息」的顺序在单体中逐个实现并随时验证；后续拆分服务时每个模块可平滑独立为单独服务并拥有自己的数据库；订单流程中的通知、库存锁定等场景能自然引入消息队列与分布式事务，完整覆盖课程技术栈（Nacos、Gateway、OpenFeign、Resilience4j、消息队列、Seata、链路追踪、Docker/K8s）。

> 作业系统「业务背景、目标用户和选题理由」填写稿（不少于 100 字符）：
> 本项目面向高校校园二手交易场景：每年毕业季学生产生大量仍有使用价值的闲置物品却缺乏高效的校内流转渠道，同时新生和在校生有低价购置需求。平台目标用户为在校学生（买家/卖家）与平台管理员，提供商品发布、搜索、下单、站内沟通与评价功能。选择该题目是因为业务贴近真实校园生活、边界清晰，且业务天然划分为用户、商品、订单、消息等模块，与微服务拆分边界高度吻合，便于本学期从单体逐步演进到完整的微服务架构，并能自然覆盖消息队列、分布式事务、服务治理等课程重点内容。

### 选题确定过程

1. 候选题目：校园二手交易平台、校园订餐系统、图书借阅系统、宿舍报修系统；
2. 从四个维度对比：需求真实性、边界清晰度、微服务拆分契合度、合规风险（是否涉及支付/资金）；
3. 结论：校园二手交易平台在「拆分契合度」和「合规风险」两项上最优——订餐系统涉及模拟支付与库存扣减，借阅系统业务偏管理侧、交易闭环弱，报修系统流程过短、难以体现服务拆分的价值；
4. 最终确定 CampusTrade，并明确以「线下交付、平台不碰资金」作为边界控制手段。
